\title{EmberDB: A FHIR-Native Time-Series Storage Engine\\for Continuous Patient Monitoring}

\author{\IEEEauthorblockN{Abhinav Srivastava}
\IEEEauthorblockA{CTO, Ambra\\Abhinav@ambra911.com}}

\maketitle

\begin{abstract}
ICU monitors sample vital signs every few seconds. The standard interoperability format for those readings is HL7 FHIR Observation. General-purpose time-series databases such as InfluxDB and TimescaleDB ingest the data but drop the clinical semantics at the storage layer, which forces reconstruction at query time. \textbf{EmberDB} is a Rust time-series engine for FHIR Observation data. Each record carries a composite metric key of patient identifier, LOINC code, and unit, and the data is partitioned into 1-hour chunks behind a write-ahead log. The engine includes a suite of clinical pattern-detection algorithms; we benchmark four of them in this paper: CUSUM changepoint detection, seasonal decomposition, Mahalanobis anomaly scoring, and moving-window analysis (a PELT segmentation method is implemented but not yet benchmarked). On a synthetic MIMIC-IV workload of 500 patients, 48-hour ICU stays, and 1.7M chart\-events, EmberDB answers patient-scoped point lookups in single-digit microseconds. We benchmark it head to head against three baselines on the identical workload: an embedded SQLite store and two purpose-built time-series engines, InfluxDB 2.7 and TimescaleDB on PostgreSQL~16, both run in Docker. On this comparative workload EmberDB ingests $3.8$--$9.4\times$ faster than these systems (1.18M records/sec, against 0.12--0.31M for the baselines) and answers patient-scoped point lookups in single-digit microseconds, against hundreds to thousands of microseconds for the baselines. In a separate standalone micro-benchmark with persistence disabled, EmberDB reaches 3.2M records/sec in memory mode with sub-microsecond point queries; this is a different, no-baseline configuration and is not the figure behind the comparative ratios. The advantage narrows on cohort scans, where TimescaleDB is competitive, and InfluxDB stores the data far more compactly. Part of EmberDB's point-query advantage over the client-server baselines reflects its in-process library path versus their network round-trip, an axis we separate in the evaluation. All results are single-node, at a single scale, and use a synthetic schema; we report the cases where EmberDB loses alongside the cases where it wins.
\end{abstract}

\section{Introduction}
\label{sec:intro}

ICU bedside monitors sample vital signs (heart rate, blood pressure, oxygen saturation, respiratory rate, temperature) at intervals from one second to a few minutes. Across a hospital that adds up to millions of observations per patient-day~\cite{johnson2016mimic}. HL7 FHIR has become the standard wrapper for these readings. Each measurement is an \texttt{Observation} resource carrying a LOINC-coded type, a numeric value with units, a patient reference, and a timestamp~\cite{hl7fhir}.

The open problem is storing those observations efficiently without losing the clinical structure. InfluxDB~\cite{influxdb} and TimescaleDB~\cite{timescaledb} can absorb the throughput, but neither preserves the structured relationship between patient, observation code, and clinical context. InfluxDB flattens FHIR into measurement/tag/field triples. TimescaleDB keeps the relational schema but pays row-storage and SQL-parsing overhead on every high-frequency point lookup, and plain PostgreSQL needs joins to answer temporal queries because it has no time-partitioned storage of its own.

EmberDB is a Rust time-series storage engine built around continuous patient monitoring. Its observations carry composite metric keys that encode patient ID, LOINC code, and unit, so a patient-scoped read is a prefix match and nothing has to map back to FHIR after ingestion. Data is bucketed into configurable time chunks, one hour by default, so range scans touch only the relevant chunks and retention can drop whole chunks at once. A write-ahead log with chunk-level durability markers handles crash recovery without slowing ingestion. A set of pattern-detection algorithms runs inside the engine, on the same data path as persistence. This paper benchmarks four of them (CUSUM changepoint, seasonal decomposition, multivariate Mahalanobis anomaly detection, and moving-window analysis); a PELT segmentation method is also implemented in the engine but is not benchmarked here.

We evaluate EmberDB on synthetic MIMIC-IV chart\-events and benchmark it head to head against three baselines on the identical workload: SQLite, InfluxDB 2.7, and TimescaleDB on PostgreSQL~16. We report where it wins and where it loses.

\section{Background and related work}
\label{sec:related}

\subsection{Clinical time-series data}
Clinical streams differ from IoT or infrastructure metrics in ways that matter for storage. The signals are multivariate and physiologically correlated, so heart rate, blood pressure, and SpO2 do not move independently. Each value also carries semantics that have to survive end to end: a LOINC code, a patient reference, and clinical context. Sampling is irregular too, with the measurement frequency set by patient acuity and clinical protocol rather than a fixed cadence.

MIMIC-IV \cite{johnson2023mimic} is the reference dataset for these properties. Its \texttt{chartevents} table runs to hundreds of millions of rows across thousands of ICU stays, with item IDs that map to specific physiological measurements.

\subsection{Existing storage approaches}
InfluxDB organizes data by measurement name with tag-based indexing, which suits infrastructure monitoring. Storing FHIR Observations means flattening each one into measurement/tag/field triples, and that discards the structured patient/code/value relationship.

TimescaleDB adds time-partitioned hypertables to PostgreSQL. The relational schema survives, but row-based storage and SQL parsing stay on the hot path for high-frequency point lookups.

SQLite is a common embedded choice for clinical applications, and its simplicity is the appeal. The cost is the absence of time-aware partitioning and the manual index management that temporal queries then require.

OpenTSDB and QuestDB are purpose-built time-series stores. Like InfluxDB, both treat every metric as a generic numeric stream with no first-class notion of a healthcare resource model.

\section{System design}
\label{sec:design}

\subsection{Architecture overview}
EmberDB is written in Rust and exposes both a library API and a REST interface built on \texttt{warp}. Internally it has three layers: an in-memory chunk manager, a write-ahead log for durability, and a JSON chunk persistence layer.

\subsection{FHIR-native metric encoding}
Each FHIR Observation becomes an internal \texttt{Record} with a composite metric name:
\begin{lstlisting}
metric_name = "{patient_id}|{loinc_code}|{unit}"
\end{lstlisting}
A heart rate for patient P1234 ends up stored as \texttt{P1234|8867-4|/min}. The encoding lets the engine answer both patient-scoped and code-scoped queries by prefix matching on the key, with no secondary indexes.

Multi-component observations (blood pressure, with systolic and diastolic, is the canonical case) are decomposed into records sharing a prefix. The FHIR component structure is preserved, and each component can be analysed as its own time series.

\subsection{Time-partitioned chunks}
Records live inside \texttt{TimeChunk} structures, each spanning a configurable duration (one hour by default).
A chunk contains a \texttt{HashMap<String, Vec<Record>{}>} mapping metric names to sorted record vectors, a resource-type index mapping FHIR resource types to their constituent metric names, and a small block of metadata (creation time, record count, dirty flag).
The chunk boundary for any timestamp is computed by flooring to the nearest multiple of the chunk duration, which keeps chunk identification at $O(1)$.

\subsection{Write-ahead log}
The WAL gives EmberDB crash recovery. Each record is persisted before it lands in the in-memory chunk.
Records are serialised as JSON with a 4-byte length prefix.
A chunk that crosses 10{,}000 records or 1~MB is flushed, and the matching WAL entries are marked durable at that point.
On recovery the engine loads the persisted chunks from disk and replays whatever WAL entries remain.

\subsection{MIMIC-IV data loader}
A MIMIC-IV loader module ships with EmberDB. It maps chart\-event item IDs to FHIR LOINC codes (itemid 220045 $\rightarrow$ LOINC 8867-4 for heart rate, and so on) and turns rows into \texttt{Record} structures directly. The path is zero-copy, so there is no overhead from building intermediate FHIR JSON.

\section{Pattern detection}
\label{sec:patterns}

EmberDB provides built-in pattern detection algorithms, configured via a TOML file and operating directly on stored records. We describe five algorithms below and report measured latency for four of them in Table~\ref{tab:pattern}; the PELT segmentation method is implemented but, as it has not yet been benchmarked under the same harness, is omitted from the latency table and excluded from the head count of benchmarked algorithms.

\subsection{CUSUM changepoint detection}
The Cumulative Sum (CUSUM) algorithm maintains running sums $S^+$ and $S^-$ tracking positive and negative deviations from the series mean:
\[
S^+_i = \max(0,\; S^+_{i-1} + (x_i - \mu - k))
\]
\[
S^-_i = \max(0,\; S^-_{i-1} + (\mu - k - x_i))
\]
where $k = 0.5\sigma$ is the sensitivity parameter. A changepoint is declared when either sum exceeds the threshold $h = \theta\sigma$, where $\theta$ is configurable (default 2.0).

\subsection{PELT segmentation}
The Pruned Exact Linear Time (PELT) algorithm finds the optimal segmentation by minimizing the penalized cost:
\[
\sum_{j=1}^{m+1} \mathcal{C}(y_{\tau_{j-1}+1:\tau_j}) + m \cdot \beta
\]
where $\mathcal{C}$ is the Gaussian negative log-likelihood cost for each segment and $\beta$ is the penalty term.
Changepoints with magnitude below $\theta\sigma$ are pruned.
This method is implemented in the engine but is not included in the latency benchmark of Table~\ref{tab:pattern}.

\subsection{Seasonal decomposition}
Time series are decomposed into trend $T_t$, seasonal $S_t$, and residual $R_t$ components using moving-average smoothing.
Both additive ($Y_t = T_t + S_t + R_t$) and multiplicative ($Y_t = T_t \times S_t \times R_t$) models are supported.

\subsection{Mahalanobis anomaly detection}
For multivariate anomaly detection across correlated vitals, EmberDB computes the Mahalanobis distance:
\[
D_M(\mathbf{x}) = \sqrt{(\mathbf{x} - \boldsymbol{\mu})^T \Sigma^{-1} (\mathbf{x} - \boldsymbol{\mu})}
\]
Points exceeding a configurable threshold (default 3.0) are flagged as outliers.
Metric groups can be specified explicitly or auto-detected via Pearson correlation.

\subsection{Moving window analysis}
A sliding window computes per-window statistics (trend slope, volatility, or range) and flags windows whose statistic deviates from the population by more than $\theta$ standard deviations.

\section{Evaluation}
\label{sec:eval}

We evaluate EmberDB on three benchmark suites: standalone performance, comparative analysis against SQLite, and a synthetic MIMIC-IV workload run head to head against three baselines.
All experiments were run on a single Apple Silicon machine running macOS, with EmberDB compiled in release mode (\texttt{--release}).
The two purpose-built baselines run in Docker on the same host: InfluxDB~2.7 (write via line protocol over HTTP, queries in Flux) and TimescaleDB on PostgreSQL~16 (bulk load via \texttt{COPY} into a one-hour hypertable, queries in SQL over a composite \texttt{(subject\_id, itemid, charttime)} index). SQLite uses WAL mode with \texttt{PRAGMA synchronous=NORMAL}. Every system ingests the same generated dataset (seed 42) and answers the same four clinical query shapes, so the numbers are comparable. The baseline harness is \texttt{benches/baseline\_bench.rs}, and every figure is recorded in \texttt{head\_to\_head\_results.csv}.

\textbf{Measurement methodology and its limits.}
The harness reports the arithmetic mean latency over a fixed number of repetitions per query (200 for EmberDB, SQLite, and TimescaleDB; 10--50 for the slower InfluxDB queries to bound wall-clock time). It does not currently record per-iteration samples, so we report means only and do \emph{not} report median, p99, or a dispersion measure; nor do we apply an explicit warmup-discard step. The microsecond-scale deltas between EmberDB and SQLite on point queries should therefore be read as order-of-magnitude indicators rather than statistically tested differences, and the lower InfluxDB iteration count makes its means correspondingly noisier. Adding an equal, larger iteration budget with warmup discard and full latency distributions is the obvious next hardening step and is left to future work.

\textbf{In-process versus client-server paths.}
The four systems do not share a client path, and this matters for interpreting the query numbers. An EmberDB query is an in-process library call with no serialization or transport. A TimescaleDB query crosses a local PostgreSQL socket and is parsed and planned as SQL. An InfluxDB query is an HTTP round-trip whose body is a Flux program compiled on every invocation. A meaningful share of the InfluxDB gap in particular --- its 4{,}949~$\mu$s single-vital point query against EmberDB's 4.0~$\mu$s --- is therefore transport and query-compilation overhead inherent to a client-server engine, not storage-layer cost, and is not the same axis of comparison as EmberDB's embedded design. We did not instrument the engines to separate the transport component numerically; readers should attribute the largest InfluxDB deltas partly to the client path rather than entirely to the storage engine.

\subsection{MIMIC-IV synthetic workload}

We generated synthetic MIMIC-IV chartevents for 500 patients, each with a 48-hour ICU stay and 6 vital signs sampled every 5 minutes (576 measurements per vital per patient).
Vital sign distributions were calibrated to published ICU ranges: HR $\mathcal{N}(84, 17)$, SBP $\mathcal{N}(121, 23)$, DBP $\mathcal{N}(70, 14)$, SpO2 $\mathcal{N}(96.8, 2.8)$, RR $\mathcal{N}(18, 4)$, Temp $\mathcal{N}(98.6, 1.2)$~\textdegree F.
Each chartevent was mapped to a FHIR Observation via LOINC code and ingested into both EmberDB and SQLite.

\subsubsection{Ingestion}
The dataset contains 1{,}728{,}000 chartevents (500 patients $\times$ 6 vitals $\times$ 576 measurements).
EmberDB ingested the FHIR-converted records at 1{,}176{,}849 records/sec (1.47s total). On the same data, SQLite reached 124{,}863 records/sec, TimescaleDB 309{,}707 records/sec via \texttt{COPY}, and InfluxDB 287{,}412 records/sec via the line protocol. EmberDB is $9.4\times$ faster than SQLite and $3.8\times$ faster than TimescaleDB, the fastest of the purpose-built baselines on ingestion.
This 1.18M records/sec is the comparative, apples-to-apples figure against which the $3.8$--$9.4\times$ ratios are computed. It is lower than the 3.2M records/sec of the standalone memory-mode micro-benchmark in Table~\ref{tab:write} because that micro-benchmark runs with persistence disabled and no baseline alongside it; the two figures describe different configurations and should not be conflated.

The two patient-scoped point queries follow the same pattern. \section{Discussion}
\label{sec:discussion}

\textbf{FHIR-native advantages.}
By encoding patient ID and LOINC code directly into the metric key, EmberDB removes the need for secondary indexes or joins when retrieving patient-scoped observations.
The design fits clinical dashboard queries that retrieve all vitals for a single patient over a shift or stay.

\textbf{Pattern detection at the storage layer.}
Embedding changepoint detection and anomaly scoring directly in the storage engine avoids data export overhead. Real-time alerting pipelines can operate on the same data path as persistence.

\textbf{Where EmberDB loses.}
The JSON chunk format is the main weakness. On the MIMIC workload it costs 201.4 bytes/record on disk, against 129.6 for TimescaleDB, 103.1 for SQLite, and 26.8 for InfluxDB, whose TSM columnar compression is $7.5\times$ more compact. Two query shapes also go against EmberDB. On the full-patient-stay query SQLite wins (747~$\mu$s vs.\ 1{,}146~$\mu$s) because EmberDB issues a separate range query per vital metric while SQLite returns every vital in one index scan. On the cohort scan TimescaleDB wins (847~$\mu$s vs.\ 968~$\mu$s) for the same structural reason: its item-indexed hypertable answers the window in a single query rather than 500 per-patient lookups. Both follow from the prefix-keyed layout, and a columnar chunk format with a multi-metric range API would address them.

\textbf{Other limitations.}
The single-writer architecture limits concurrent write throughput. The pattern-detection algorithms use simplified implementations; a production deployment would need validated statistical libraries.

\textbf{Scope of the evaluation.}
Every measurement here is single-node, at a single scale, and uses a synthetic schema. The entire cross-system comparison is one 1.728M-record point at one cardinality on one Apple Silicon host; we have not run it at a second scale or on real MIMIC-IV \texttt{chartevents}, so claims that the ordering generalizes are hypotheses, not results. The workload is generated from published ICU vital-sign distributions rather than real \texttt{chartevents}, and all four systems ran on one machine, so the numbers capture single-host engine behavior, not clustered or networked deployment. Because the systems are exercised through different client paths --- an in-process call for EmberDB versus a socket or HTTP round-trip for the server engines --- the query-latency multiples conflate storage-engine cost with transport and query-compilation overhead, and we did not separate the two numerically. The point/range query mix also favors a prefix-keyed store and omits the analytical scans (time-bucketed downsampling, multi-tag aggregation, gap-fill) that InfluxDB and TimescaleDB are tuned for; adding one or two such queries is needed before the head-to-head can be called balanced, and we flag the current mix as tilted toward EmberDB. We therefore frame the relative ordering as a hypothesis to be confirmed: a second scale, a real-data run, and the missing analytical query shapes would each de-risk it, and the absolute figures and the storage gap in particular would shift with a columnar format and a real workload.

\textbf{Future work.}
Planned improvements include columnar chunk encoding (e.g., Parquet), concurrent chunk writers with sharded locking, integration with FHIR Subscription for push-based alerts, and support for FHIR Bulk Data export.

%---------------------------------------------------------------------
\section{Conclusion}
\label{sec:conclusion}

EmberDB shows that high ingest throughput and native clinical semantics are not mutually exclusive. Encoding patient identity and LOINC codes into the storage key, partitioning the data into time-aligned chunks, and integrating the pattern-detection algorithms directly yields a system that handles continuous patient monitoring without giving up time-series performance.
On the synthetic MIMIC-IV workload it ingests $3.8$--$9.4\times$ faster than SQLite, TimescaleDB, and InfluxDB and answers patient-scoped point queries in single-digit microseconds, while preserving FHIR structure with no post-hoc transformation. It is not uniformly faster: TimescaleDB matches it on cohort scans and InfluxDB stores the data in a fraction of the space, both of which point to the columnar chunk format as the next step. These results come from a single synthetic scale on one host, measured as means without latency distributions and through engine-specific client paths, so we present the ordering as a hypothesis: confirming it calls for a second scale, a real-data run, the analytical query shapes the current mix omits, and full latency distributions over an equal iteration budget.
